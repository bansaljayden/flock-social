# Maestro flow audit, 2026-09-01

Read-only check of `apple-2-1.yaml` and `parts/{signup,login,logout,open-chat}.yaml`
against the source. Line numbers are from the tree as of this audit; App.js line
numbers drift, so the searchable string is given alongside each one.

How Maestro matches on iOS, verified against the driver source
(`maestro-client/src/main/java/maestro/drivers/IOSDriver.kt`, `maestro/Filters.kt`):

- `text:` is a whole-string regex tested against the element's `text`
  (XCUIElement `title`, else `value`) OR its `accessibilityText` (XCUIElement
  `label`). In a WKWebView the `label` is the accessible name, so an
  `aria-label` REPLACES the visible text for matching purposes, and a
  `<label for>` becomes the input's label. An empty input's `value` is its
  placeholder, which is why placeholder taps work.
- `id:` is tested against `resource-id`, which the driver fills from XCUIElement
  `identifier`. WebKit does not put a DOM `id` there. Every `id:` selector in
  these flows (`signup-dob`, `Vote on a venue`, `Accept invite`,
  `delete-password`) matches nothing on iOS.
- `back` is `override fun backPress() {}` on iOS (no-op). The docs say
  "currently supported only on Android and Web". All four `- back` steps do
  nothing.
- `hideKeyboard` on iOS does two 3 percent swipes at the screen centre and
  never presses a key. The docs' own workaround is to tap a non-interactive
  element.
- The XCTest hierarchy handler does not drop occluded elements, so a button
  under the keyboard is still "found" and the tap lands on the keyboard.

## 1. Why `Tap on "Sign in"` fails, and the fix

The submit button is the only element on the login screen whose label is
exactly `Sign in` (`LoginScreen.js:299-301`; the Apple button reads
`Continue with Apple`, `AppleSignInButton.js:78`, Google reads
`Continue with Google`, `LoginScreen.js:323`, and the heading is
`Welcome back`, `LoginScreen.js:146`). It is never disabled before submit
(`disabled={loading}`, loading only flips inside handleSubmit). So the selector
is right and the button exists; what is wrong is the state of the screen when
the tap fires.

`parts/login.yaml` types the password and then relies on `hideKeyboard`
(`login.yaml:9`). On iOS that command only nudges the screen centre, and in
this app the auth screens scroll inside their own `100dvh; overflow-y: auto`
container (`AuthShell.js:242-244`) with the native scroll view disabled
(`capacitor.config.ts` `ios.scrollEnabled: false`), so nothing dismisses the
keyboard and `Sign in` stays under it. `parts/signup.yaml` never hits this
because it taps the hero heading `Create your account` before `Create account`
(`signup.yaml:44-46`), which blurs the field and closes the keyboard. Login has
no equivalent step.

Fix in `parts/login.yaml`, replacing line 9-10:

```yaml
- tapOn: "Welcome back"      # LoginScreen.js:146, non-interactive, closes the keyboard
- tapOn: "Sign in"
```

(`pressKey: enter` after the password is a reasonable second option: the form
is a real `<form onSubmit>` with `noValidate`, `LoginScreen.js:183`, so the
return key submits it. Keep the heading tap as the primary fix because it
mirrors what already worked in signup.)

Where that failure most likely came from: the main flow cannot have reached
`parts/login.yaml` at all (section 2 below), but `apple-2-1-cleanup.yaml` runs
afterwards with `|| true` and starts with `parts/login.yaml` on a clean
launch. Its `Tap on "Sign in"` is the one that would show as the last failure
in the log.

## 2. Blockers that stop the recording before shot 6, in order

### 2a. Signup never lands on Nest

`POST /api/auth/signup` always answers `emailVerificationRequired: true`
(`backend/routes/auth.js:2180`, unconditional). `SignupScreen.js:182-189`
then renders the `Confirm your email` screen and never calls
`onSignupSuccess`, so `signup.yaml:50-52` (`extendedWaitUntil visible: "Nest"`)
times out. The token IS stored by the api wrapper (`services/api.js` signup,
`setToken(data.token)`), and login does not require verification ("The account
exists and can sign in", `auth.js:2160`).

Correction, `parts/signup.yaml` after `tapOn: "Create account"`:

```yaml
- extendedWaitUntil:
    visible: "Confirm your email"          # SignupScreen.js:211
    timeout: 25000
- tapOn: "Sign in"                          # SignupScreen.js:239 -> LoginScreen
- runFlow:
    file: login.yaml
    env: { EMAIL: ${EMAIL}, PASSWORD: ${PASSWORD} }
```

That also puts shot 3 (the verification screen) on camera for free.

### 2b. Unverified accounts cannot create a flock, invite, or befriend

`backend/middleware/auth.js:176-201` `UNVERIFIED_DENY` refuses
`POST /api/flocks`, `POST /api/flocks/:id/(join|invite|invite-link|rerun)` and
`POST /api/friends/(request|accept|add-by-code)` for any account whose email
is not verified, with 403 `emailVerificationRequired`. The client turns that
into the `Confirm your email first` sheet (`VerifyEmailSheet.js:51`). Both
review accounts are minted fresh by the workflow (`codemagic.yaml:497-501`)
and nothing verifies them, so shots 6 through 13 cannot happen.

Options, both outside the flow files:
- Verify each account after signup by fetching the sent mail through Resend's
  API and hitting the link it carries
  (`GET /api/auth/verify-email?token=…`, `backend/routes/auth.js:2227`,
  built at `backend/services/emailService.js:770`). The workflow already has
  the account addresses in shell variables.
- Or point `REVIEW_EMAIL_A/B` at two pre-verified accounts and drop the
  signup shots from the flow.

### 2c. Inviting one person on the create screen makes a DM, not a flock

`CreateScreen.js:156`: `dmTarget = flockFriends.length === 1 && …`. With only
B added the footer reads `Just Sam Review`, the button reads `Message Sam`
(`CreateScreen.js:576`) and the copy at `:559` says it opens a direct message.
`Review night` would never exist as a flock. The create-screen search also
finds any user (`backend/routes/users.js` search, `name ILIKE`), but the DM
rule still applies.

Correction for `apple-2-1.yaml:72-81`: delete the invite block. Create the
flock alone, then get B in through the chat's `Invite friends` modal
(`ChatDetail.js:529` header control behind the `Features` pill at `:533`, or
`:911` in the empty chat). That modal searches FRIENDS only
(`flockInviteAllFriends`, `ChatDetail.js:2040-2060`), so A and B must be
friends first: A `You` > `Add Friends` (`ProfileSettings.js:634`) > `Search
by name...` (`AddFriends.js:222`) > type name > `Add` (`AddFriends.js:264`),
then B `Add Friends` > `Accept friend request` (`AddFriends.js:191`). That is
two more screens, and both calls are on the 2b deny list, so 2b has to be
solved first either way.
